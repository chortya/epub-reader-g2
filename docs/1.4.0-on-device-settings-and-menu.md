# v1.4.0 Design — On-Device Main Menu, Settings, Mode Switch, Clock

**Status:** Rev. 3 — open decisions resolved via interview (see §16). Phase 1 scope locked. §§4.2, 6.1 updated with the picked value set and gesture semantics; §12.2 retired in favour of §16. Not yet implemented.
**Author:** Andriy (with Claude architect-mode collaboration)
**Target version:** 1.4.0
**Current version:** 1.3.1
**Touches:** `types.ts`, `constants.ts`, `even-client.ts`, `main.ts`, `paginator.ts`, `index.html`, tests, docs
**Estimated complexity:** Complex (new top-level IA, new ViewState values, settings editor, gesture repurposing, clock ticker, removal of a deprecated option)

---

## 1. Summary

v1.4.0 elevates the reader's on-device interaction model from a single-screen list-of-books into a proper three-pane home screen, and brings the entire settings surface onto the glasses so the user no longer has to reach for the phone to change hyphenation, reading mode, flow speed, text height, or status-bar layout. The design also retires the vertical (right-side) status bar option, adds a clock to the horizontal status bar, and proposes a minimal-gesture way to flip between **Paged** and **Flow** reading modes without leaving the reading view.

Five user-visible changes in the full design surface:

1. **Main Menu** after splash with three items: `Continue reading`, `Library (N)`, `Settings`.
2. **On-device Settings** — a sub-menu replicating the five settings from the web UI (hyphenation, status bar position, reading mode, flow speed, text height). Each setting is edited via a uniform list-based editor (no sliders, no steppers — just a list of valid values with the current one pre-selected).
3. **Quick mode switch** during reading via a currently-unused gesture slot (see §6). This is **deferred to v1.4.1** by the Phase 1 lock in §13; it remains documented here so the later gesture work does not need to be re-derived.
4. **Clock in the horizontal status bar** — `HH:MM` left-aligned, progress information right-aligned, updated via `textContainerUpgrade` once per minute.
5. **Removal of the vertical ("right") status bar** — the option is dropped from the `AppConfig` enum, from the web UI, and from all rendering paths. Persisted `'right'` values migrate to `'bottom'` on read (precedent: the `showStatusBar → statusBarPosition` migration from v0.8.0).

Non-goals (out of scope for v1.4.0): see §11.

## 2. Current State (what we're changing)

### 2.1 ViewState

```ts
// src/types.ts
export type ViewState = 'bookPicker' | 'library' | 'reading' | 'flowReading';
```

- `bookPicker` is the list of cached books shown on startup.
- `library` is the chapter list inside an opened book **and** the "welcome" (no-book) screen — those share one state, distinguished by `this.book !== null`.
- `reading` is paged reading; `flowReading` is the word-by-word streamer.

### 2.2 Gesture surface (fixed, not extensible)

The Even Hub SDK emits exactly four user-driven events (`src/even-client.ts:919-993` wraps the dispatch, `even-toolkit/action-map` normalizes to three action types):

| SDK event              | toolkit action      | Used today in each view                                                         |
|------------------------|---------------------|---------------------------------------------------------------------------------|
| `SCROLL_TOP_EVENT`     | `HIGHLIGHT_MOVE up` | prev page / prev chapter / prev list item                                       |
| `SCROLL_BOTTOM_EVENT`  | `HIGHLIGHT_MOVE down`| next page / next chapter / next list item                                      |
| `CLICK_EVENT`          | `SELECT_HIGHLIGHTED`| open book / open chapter / start-pause flow; **unused in paged `reading`**     |
| `DOUBLE_CLICK_EVENT`   | `GO_BACK`           | back to chapter list / picker / exit app                                       |

There is **no long-press**, **no triple-tap**, **no temple-swipe-forward/back** at the SDK level. Any feature proposal that needs a fifth gesture is dead on arrival. The only free slot today is **tap in paged `reading`**, which the current code ignores (see `onEvenHubEvent.SELECT_HIGHLIGHTED` — no `'reading'` branch).

### 2.3 Status bar rendering

Three code paths render `config.statusBarPosition`:

- `even-client.ts:429-496` — `showPage()` builds `[textContainer, footer|sidebar]`.
- `even-client.ts:559-622` — `showFlowFrame()` rebuild path.
- `even-client.ts:634-653` — `showFlowFrame()` `textContainerUpgrade` path.

All three branch on `hasBottomBar` / `hasRightBar`. `paginator.ts:25` and `even-client.ts:183` also read the position to compute `maxChars`.

`getTextLayout()` in `constants.ts:132-161` only reserves height for the bottom bar — the right bar is drawn over reserved width in the caller, not in the shared layout primitive. That asymmetry is why the "right" branch is spread across three files instead of one.

### 2.4 Settings pipeline (as of v1.3.1)

- `constants.ts:37-43` defines the default `config: AppConfig`.
- `loadSettings(raw)` (pure, exhaustively tested) validates and clamps an incoming JSON blob.
- Sync module-load: `Object.assign(config, loadSettings(localStorage.getItem(SETTINGS_KEY)))` — browser LS is the warm-start source.
- `loadSettingsFromBridge(bridge)` (new in v1.3.1) runs after `waitForEvenAppBridge` resolves and overrides with bridge-persisted values.
- `saveSettings()` writes browser LS; `saveSettingsToBridge(bridge)` writes the persistent bridge store.
- `client.applySettings()` re-paginates, rescales page indices, and refreshes the active view.

New on-device settings will reuse this pipeline entirely. No new persistence lane.

## 3. New Information Architecture

### 3.1 Target state machine


Key transitions that **change** vs v1.3.1:

| From → To                         | v1.3.1 behavior                            | v1.4.0 behavior                                          |
|-----------------------------------|--------------------------------------------|----------------------------------------------------------|
| splash → ?                        | `bookPicker` if cached books; else welcome | `mainMenu` always                                        |
| `bookPicker` dbl-tap              | exit app                                   | `mainMenu`                                               |
| `library` dbl-tap (no book open)  | exit app                                   | `mainMenu`                                               |
| `library` dbl-tap (book open)     | `bookPicker` if cached; else welcome       | `mainMenu`                                               |
| `mainMenu` dbl-tap                | (did not exist)                            | exit app                                                 |
| onLaunchSource('glassesMenu')     | auto-resume last book                      | unchanged — bypass `mainMenu`, go straight to reading    |
| onLaunchSource('appMenu')         | (implicit bookPicker path)                 | unchanged — `mainMenu`                                   |

Exit-app distance from reading grows by one dbl-tap (reading→chapterList→bookPicker→exit is now reading→chapterList→mainMenu→exit). Acceptable because the `mainMenu` is the natural home and users will mostly background the app via the host OS, not via an in-app exit.

### 3.1a Startup ownership (Codex #1)

The v1.3.1 startup sequence is:

```
main.ts:102            client.init()                    // splash → pick home view (today: bookPicker)
main.ts:110            bridge.onLaunchSource(cb)        // registered AFTER init
cb fires later         auto-resume last book            // overlays whatever init rendered
```

This "race then overlay" pattern works today because the first rendered view is the same (`bookPicker`) whether the launch was `appMenu` or `glassesMenu` — `glassesMenu` only has to punch through to `reading` afterward, which is visible to the user as a short flash.

**v1.4.0 cannot keep this shape.** If `glassesMenu` is supposed to bypass `mainMenu`, the splash → first-view decision inside `runStartup` must know the launch intent *before* it picks a view. Otherwise the user sees `mainMenu` flash, then the reading view, which is worse than today's behavior.

Recommended restructuring:

1. `main.ts` registers `onLaunchSource` **before** calling `client.init()`. The callback stashes the source into a module-local or `client`-local `launchIntent` variable (`'appMenu' | 'glassesMenu' | null`).
2. `EvenEpubClient.init()` accepts an optional `launchIntent` getter (or reads the module-local) after splash completes. If `launchIntent === 'glassesMenu'` and a last book is resolvable, it goes directly to `reading` / `flowReading`. Otherwise it goes to `mainMenu`.
3. If the launch source is still `null` at splash-completion time (SDK hasn't fired yet), default to `mainMenu` — the callback resolves later but the user is already on a sensible screen. This is the safe fallback that v1.3.1 implicitly relied on.

This is **new implementation work** in v1.4.0 and must not be described as "unchanged". The change surfaces in `main.ts` (registration order), `even-client.ts` (`init` signature + launch-aware splash handler), and a new test in `tests/` that exercises the decision function with mocked launch sources.

### 3.2 `mainMenu` item wiring

```
Slot 0: Continue reading                → tap → showContinueReading()
Slot 1: Library (N)                     → tap → showBookPicker()  [existing]
Slot 2: Settings                        → tap → showSettingsMenu()
```

- `N` is `cachedBookList.length` (from bridge localStorage — already maintained).
- Slot 0 shows `"Continue reading"` if a last book is resolvable, `"(No recent book)"` otherwise. A non-resolvable tap is a no-op (no beep, no state change — the highlight stays).
- `showContinueReading()` **resolves by bookId first** (Codex #2, decision Q6 → B: no legacy title fallback). v1.4.0 hard-deprecates the v1.3.1 title-only path — users upgrading without opening a book see `"(No recent book)"` until they open something, and this is called out explicitly in the v1.4.0 CHANGELOG. The resolution algorithm is:
  1. Read `STORAGE_KEY_LAST_BOOK_ID` via `bridge.getLocalStorage` (new key — see §8.3).
  2. If present and resolvable: find in `cachedBookList` by `bookId`. Done.
  3. Else read `STORAGE_KEY_BOOK_TITLE` + `STORAGE_KEY_LAST_BOOK_FILENAME` (new) and resolve by `(filename, title) → makeBookId(filename, title)` lookup.
  4. **No further fallback.** If steps 2-3 fail, Continue is treated as unresolvable — slot 0 shows `"(No recent book)"` and taps are no-ops (per Q3 → A).
  5. If a match is found in `cachedBookList`, call `onBookSelected(meta)` — the same callback `main.ts` wires for bookPicker taps. This triggers `parseEpub → loadBook(resume=true)` and the client chooses `showPage()` or `showFlowFrame()` based on `config.readingMode` and which position lane (paged/flow) was last saved.

The new `STORAGE_KEY_LAST_BOOK_ID` must be written every time the old `STORAGE_KEY_BOOK_TITLE` is written (both in `savePagedPosition` and `saveFlowPosition` in `even-client.ts`), so the two stay in lockstep. See §8.5 for the persistence invariants this depends on.

### 3.3 `rebuildSlots` reuse

The existing `rebuildSlots(labels: string[], selectedSlot: number)` primitive (`even-client.ts:672-702`) renders `ITEMS_PER_PAGE = 4` rows of `ROW_HEIGHT = 72 px`, with one `isEventCapture=1` container on the selected row. This primitive satisfies:

- `mainMenu` — 3 items, one blank slot 3.
- `settings` menu — 5 items, paginated across 2 pages (existing pagination math: `pageStart = floor(idx/4)*4`).
- `settingEditor` per-setting options lists — 2 to 12 items depending on the field.

**No new rendering primitive is introduced.** This is intentional: the list pattern is already battle-tested for the book picker and chapter list, including its event-capture rules.

## 4. On-device Settings

### 4.1 Settings list

Accessed via `mainMenu → Settings`. Rendered with `rebuildSlots`.

```
Hyphenation: ON
Status bar: Bottom
Reading mode: Paged
Flow speed: 240 wpm
Text height: 80%
```

Labels are generated from `config` at render time. The label format is `{name}: {formattedValue}` — string formatting lives in a new pure helper, e.g. `formatSettingsRow(key: SettingKey): string`, kept in `constants.ts` next to `loadSettings` so it's unit-testable without a DOM.

- Swipe up/down: move highlight (existing `HIGHLIGHT_MOVE` wiring).
- Tap: enter `settingEditor` for that key.
- Dbl-tap: back to `mainMenu`.

### 4.2 Unified setting editor (single pattern for all five)

Every setting — boolean, enum, or integer — is edited by showing a **list of valid values** with the current value pre-selected, using `rebuildSlots`. This keeps the implementation uniform and avoids inventing a stepper UI that would need its own gesture semantics.

| Setting              | Values rendered in the editor                                   | Stored as                    |
|----------------------|------------------------------------------------------------------|------------------------------|
| `hyphenation`        | `["ON", "OFF"]`                                                  | `boolean`                    |
| `statusBarPosition`  | `["Bottom", "None"]`                                             | `'bottom' \| 'none'`         |
| `readingMode`        | `["Paged", "Flow"]`                                              | `'paged' \| 'flow'`          |
| `flowSpeedWpm`       | `[120, 150, 180, 210, 240, 270, 300, 330, 360, 390, 420, 450, 480, 510, 540, 570, 600]` (17 uniform 30-WPM steps; decision Q4 → B) | `number` (clamped by loader) |
| `textHeightPercent`  | `[50, 60, 70, 80, 90, 100]`                                      | `number` (clamped by loader) |

- Swipe up/down: move highlight.
- Tap: commit the highlighted value, run `client.applySettings()`, `saveSettings()`, `saveSettingsToBridge(bridge)`, then return to the settings list.
- Dbl-tap: cancel (no write), return to the settings list.

The value-set for integer settings lives in a new exported constant array in `constants.ts`:

```ts
// 17 uniform 30-WPM steps from FLOW_MIN_WPM to FLOW_MAX_WPM (decision Q4 → B).
export const FLOW_SPEED_VALUES = [
  120, 150, 180, 210, 240, 270, 300, 330, 360,
  390, 420, 450, 480, 510, 540, 570, 600,
] as const;
export const TEXT_HEIGHT_VALUES = [50, 60, 70, 80, 90, 100] as const;
```

`loadSettings` continues to clamp to `[FLOW_MIN_WPM, FLOW_MAX_WPM]` and `[TEXT_HEIGHT_MIN_PERCENT, TEXT_HEIGHT_MAX_PERCENT]` — the new constants are for **editor presentation only**, not validation. A rogue settings blob containing `flowSpeedWpm: 999` still clamps to 600 and is acceptable; the editor will just show no pre-selection match and default to the closest value.

Pre-selection algorithm: for integers, pick `argmin |v − config.x|`. For enums/booleans, exact match. Both handle edge cases without a special "unknown" state.

### 4.3 ViewState additions

```ts
// src/types.ts — proposed
export type ViewState =
  | 'mainMenu'
  | 'bookPicker'
  | 'library'
  | 'reading'
  | 'flowReading'
  | 'settings'          // settings menu (list of 5)
  | 'settingEditor';    // per-setting value picker
```

`settingEditor` needs to track *which* setting is being edited. New private fields on `EvenEpubClient`:

```ts
private editingSettingKey: SettingKey | null = null;
private editorSelectedIndex = 0;
```

`SettingKey = 'hyphenation' | 'statusBarPosition' | 'readingMode' | 'flowSpeedWpm' | 'textHeightPercent'`.

### 4.4 Applying the change

On editor commit, **the bridge write runs in parallel with repaint — never blocking the UI** (Codex #3). This matches v1.3.1's settings-apply handler in `main.ts:220-235`, where the bridge write is kicked off, `applySettings` runs immediately, and the bridge promise is only awaited at the end for the "Settings applied." status string.

```ts
async commitEditor() {
  if (!this.editingSettingKey) return;
  applyEditorValue(config, this.editingSettingKey, this.editorSelectedIndex);

  // Fire-and-forget bridge write — do not await before repaint.
  saveSettings();                                       // sync, browser LS mirror
  const bridgeWrite = saveSettingsToBridge(this.bridge) // async, device-persistent
    .catch((e) => console.warn('commitEditor bridge write failed:', e));

  await this.applySettings();                           // repaginate + refresh (not blocked)
  await this.showSettingsMenu();                        // back to list (not mainMenu)

  // Await at the end so uncaught rejections still surface, but the user has
  // already seen the updated UI. If the bridge was flaky (Flutter-handler
  // regression documented in v1.3.1), the user's in-session change is lost on
  // next app restart — acceptable degraded state.
  await bridgeWrite;
}
```

`applyEditorValue` is a pure function (unit-testable): given the key and the index into the editor's value array, it writes the correct slot on `config`. Separating it from the view layer is deliberate — `applySettings` already handles re-pagination consequences.

**Side effect of changing `readingMode` in-editor:** `applySettings()` already transitions `view='reading' ↔ view='flowReading'` on mode change (see `applySettings` lines 161-170). We do NOT want that to happen when the user is inside `settingEditor` — we want to return to `settings` first and let the user pick `mainMenu → Continue reading` (or back out to it manually) to re-enter reading. This means `applySettings` needs to **early-return** the auto-view-switch branch when `view === 'settings' || view === 'settingEditor'`, and only repaginate. Implementation note for Phase 4 below.

## 5. Removal of the Vertical Status Bar

### 5.1 Why remove

- It's visually cramped (26 px wide × 288 px tall, a 10-segment bar).
- It breaks the "paginator computes `maxChars` from a layout primitive" abstraction — only the vertical bar steals width instead of height, forcing every caller to duplicate the 26 px subtraction (`even-client.ts:439, 568, 611`).
- Adding the clock to it is awkward — there's no room for `"HH:MM"` vertically.
- No known user requests for it.

### 5.2 Removal checklist

- `types`: drop `'right'` from `AppConfig.statusBarPosition` (already fixed precedent: `loadSettings` previously had a `showStatusBar → statusBarPosition` migration).
- `loadSettings`: drop the `'right'` branch; add migration — if `parsed.statusBarPosition === 'right'`, set `out.statusBarPosition = 'bottom'`. New test case.
- `paginator.ts`: simplify `maxChars` default to `wideGlyphs ? 48 : 59`.
- `even-client.ts`:
  - delete `hasRightBar`, `rightBarWidth` variables and the `else if (hasRightBar)` branches in `showPage`, `showFlowFrame` (rebuild path and upgrade path).
  - `textWidth` becomes just `DISPLAY_WIDTH`.
  - `maxChars` in the welcome container (`even-client.ts:183`) simplifies to `59`.
- `main.ts`: remove the `'right'` case from `statusBarConfig.value = ...` assignment.
- `index.html`: remove `<option value="right">Right</option>` from `#setting-statusbar`.
- Tests: delete the "accepts all three statusBarPosition values" case from `tests/settings-persistence.test.ts`, replace with "accepts two values; 'right' migrates to 'bottom'".

No user-facing data loss — users currently on `'right'` simply get `'bottom'` after upgrade. The right-bar rendering code has no other callers.

## 6. Quick Paged ↔ Flow Mode Switch

This is the **only part of the design with no clean solution**, because the gesture surface is saturated in flow mode (tap = start/pause, swipe = chapter nav, dbl-tap = back). Three options considered; **Option A** is recommended as the primary proposal. The other two are preserved for the reviewer to weigh in.

### 6.1 Option A (recommended) — Asymmetric tap switch

**Paged reading (`view='reading'`):**
- Tap: enter `flowReading` at the current paged position, auto-start. This re-purposes a currently-ignored gesture slot.
- Dbl-tap: back to chapter list (unchanged).

**Flow reading (`view='flowReading'`):**
- Tap: toggle start/pause (unchanged).
- Dbl-tap when **running**: **no-op** (decision Q1 → A1). Defensive; user must tap to pause before exiting. Preserves the v1.3.1 gate at `even-client.ts:976`.
- Dbl-tap when **paused**: switch to `reading` at the current flow position (changed from today's "back to chapter list").

**Getting from flow mode to chapter list** becomes: pause (tap) → switch to paged (dbl-tap) → back (dbl-tap). Three gestures instead of two, paid exclusively by users who want the chapter list directly from flow — judged a fair trade for the always-available mode switch.

### 6.2 Option B — Sacrifice flow's start/pause tap

Tap in both paged and flow reading switches mode. Flow's start/pause migrates to… nothing exists. This is a non-starter unless we give up the pause feature entirely, or require the user to go to `mainMenu → Continue` each time they want to resume. **Rejected.**

### 6.3 Option C — Reader action overlay

Double-tap from reading opens a mini-menu (`view='readerActions'`) with `[Switch mode, Chapter list, Main menu]`. Swipe/tap to pick. Three screens deep instead of two. Works for every transition but makes every back-out slower. **Viable if the reviewer thinks tap-in-paged is too discoverability-poor; preserved as fallback.**

### 6.4 Discoverability problem (applies to A)

A tap in paged mode doing "nothing today, mode-switch tomorrow" is a hidden affordance. Mitigations:

1. **Release notes / README**: document the gesture in the controls table.
2. **Status bar hint on first use**: the first N entries into `reading` after a v1.4.0 upgrade append `" • Tap=Flow"` to the footer label for ~10 seconds / until the user taps. Gated by a new one-shot flag `epub-reader-seen-mode-switch-hint` in bridge storage.
3. **Settings → Reading mode** still switches modes globally, so users who never discover the gesture still have a path.

## 7. Clock in the Horizontal Status Bar

### 7.1 Format

Bottom status bar (30 px × 576 px, one line of ~59 Latin / ~48 Cyrillic chars):

```
HH:MM  Ch C/T Pg P/N [━━━──────]
```

- `HH:MM` uses the device WebView's `new Date()` — whatever the Even Hub host clock says. 24-hour format, zero-padded.
- Separator: two spaces (trims cleanly; single `|` adds noise).
- Progress bar length is already computed dynamically: `targetBarLen = maxChars − infoText.length − 2`. With `HH:MM + 2 spaces + ` (6 chars) prepended to `infoText`, the bar shrinks by 6 chars — e.g. from ~16 to ~10 glyphs at typical chapter/page widths. Still informative.

### 7.2 Where the string is assembled

A new pure helper in `constants.ts`:

```ts
export function formatStatusLine(args: {
  now: Date;                    // injected, test-friendly
  infoText: string;             // "Ch 1/12 Pg 42/100 "
  maxChars: number;             // 59 (Latin) / 48 (Cyrillic)
  progress: number;             // 0..1
}): string
```

Returns the full footer content including the bar. This replaces the inline string building in `showPage` and `showFlowFrame` and is unit-testable against mutation (`if >` boundaries, maxChars edges, 0/1 progress, midnight rollover).

### 7.3 Ticking

A new private `clockTickerId: number | null` on `EvenEpubClient`. Lifecycle:

```
enterReading()   → startClockTicker()
enterFlow()      → startClockTicker()
leaveReading()   → stopClockTicker()
leaveFlow()      → stopClockTicker()
FOREGROUND_EXIT  → stopClockTicker()
FOREGROUND_ENTER → startClockTicker() if view ∈ {reading, flowReading}
```

`startClockTicker`:
- Cache `this.lastMinuteString = 'HH:MM'`.
- `setInterval` every 10 s. On each tick, compute current `HH:MM`; if equal to cached, skip; else update cache and call `textContainerUpgrade(containerID=footer, content=formatStatusLine(...))`.
- 10 s is a compromise — the minute can roll over ≤ 10 s after we miss it, which is user-acceptable jitter. Finer granularity wastes bandwidth on a display that isn't animated.

`stopClockTicker`:
- `clearInterval(this.clockTickerId)`; `this.clockTickerId = null`.

### 7.4 Interaction with page turns

Page turns already call `rebuildPageContainer` (paged) or `textContainerUpgrade` (flow-frame upgrade path). Both recompute the full status string, so the clock is fresh on every page turn regardless of the ticker. The ticker is only needed between page turns.

A race is possible: the ticker fires at the same moment as a page turn. Both write the same container — last-writer-wins is fine since both compute the same minute string. No locking needed.

**Important invariant** for the paged path: the ticker upgrades container `ID=2, name='footer'` in place using `textContainerUpgrade`. Today, `showPage` only renders that footer via `rebuildPageContainer` (unlike `showFlowFrame`, which already has a two-branch rebuild/upgrade pattern). We are **introducing** the requirement that the paged reading container layout is stable enough to support in-place text updates on container 2. That's fine because the container geometry for the footer never changes mid-page (only its content does), but the invariant needs to be documented and tested: if a future change moves the footer container ID, the ticker breaks silently. A unit test over `formatStatusLine` plus a simulator smoke-test (clock advances without flicker on a stationary page) are the mitigations.

### 7.5 No clock in non-reading views

Out of scope. The user specified "in the horizontal status" — reading-view scope. `bookPicker`, `mainMenu`, `settings`, `library` keep their current layouts.

## 8. Data Model & Migration

### 8.1 `AppConfig` shape (unchanged number of fields)

```ts
export type AppConfig = {
    hyphenation: boolean;
    statusBarPosition: 'bottom' | 'none';   // CHANGED: 'right' removed
    readingMode: 'paged' | 'flow';
    flowSpeedWpm: number;
    textHeightPercent: number;
};
```

No new config fields. The clock is always on in reading views (it's part of the bottom bar content, not a toggleable feature — if the user hides the bar entirely via `statusBarPosition='none'`, the clock goes with it).

### 8.2 Migration logic in `loadSettings`

```ts
// src/constants.ts — modified
if (
    parsed.statusBarPosition === 'bottom'
    || parsed.statusBarPosition === 'none'
) {
    out.statusBarPosition = parsed.statusBarPosition;
} else if (parsed.statusBarPosition === 'right') {
    out.statusBarPosition = 'bottom';       // NEW migration
} else if (typeof parsed.showStatusBar === 'boolean') {
    out.statusBarPosition = parsed.showStatusBar ? 'bottom' : 'none';
}
```

### 8.3 Bridge storage keys

- `SETTINGS_KEY = 'epub-reader-settings'` — **unchanged.** All new settings fold into the existing JSON blob.
- `STORAGE_KEY_LAST_BOOK_ID` — **new.** Persisted by every `savePagedPosition` / `saveFlowPosition` call alongside the existing `STORAGE_KEY_BOOK_TITLE`. Enables the bookId-first Continue Reading resolution in §3.2.
- `STORAGE_KEY_LAST_BOOK_FILENAME` — **new, optional.** Same write cadence; used as tiebreaker when bookId is missing and multiple titles collide.

No new bridge-storage *lane* — all three keys live in the same `bridge.setLocalStorage` store already in use.

### 8.4 Compatibility with v1.3.1 installs

Forward-compatible: a v1.3.1 blob `{statusBarPosition: 'right', readingMode: 'paged', ...}` under v1.4.0 loads as `{statusBarPosition: 'bottom', ...}`. No data loss since the user's visible configuration already treats 'right' as nearly identical to 'bottom' (both imply "show progress").

Backward-compatible (user downgrades): not guaranteed for `AppConfig`. A user who downgrades from v1.4.0 → v1.3.1 keeps their last-saved settings, which are a valid v1.3.1 blob. No field was added or removed in the JSON shape. The new `STORAGE_KEY_LAST_BOOK_ID` / `STORAGE_KEY_LAST_BOOK_FILENAME` keys are simply ignored by v1.3.1 — no conflict.

### 8.5 Persistence invariants for Continue Reading (Codex #5)

`mainMenu → Continue reading` is correct only if three stores stay consistent, and the design **must** define fallback behavior when one of them drifts. The three lanes:

| Lane | Key                                 | Writer                                                                           | Read by                |
|------|-------------------------------------|----------------------------------------------------------------------------------|------------------------|
| L1   | `epub-book-list`                    | `EvenEpubClient.cacheBookList()` — every time `main.ts` renders the web library  | Glasses-side picker, mainMenu "Library (N)" count, Continue Reading resolver |
| L2   | `STORAGE_KEY_POSITION + {bookId\|title}`, `STORAGE_KEY_FLOW_POSITION + …` | `savePagedPosition()`, `saveFlowPosition()` in `EvenEpubClient` | `restorePagedPosition`, `restoreFlowPosition` |
| L3   | `STORAGE_KEY_BOOK_TITLE`, `STORAGE_KEY_LAST_BOOK_ID` (new), `STORAGE_KEY_LAST_BOOK_FILENAME` (new) | Same writers as L2, written adjacent to position data | Continue Reading resolver (new) |

**Invariants the design depends on:**

- **I1 — L3 consistency**: every time L2 is written, L3 is written with the same `(bookId, title, filename)`. Today v1.3.1 writes `STORAGE_KEY_BOOK_TITLE` on both save paths; v1.4.0 adds the two new keys to the same call sites. A partial write (title written but bookId failed) is acceptable — resolver falls back to title lookup.
- **I2 — L1 superset of resumable books**: if L3 points to a `bookId`, it must appear in L1. Otherwise the user sees "Continue reading" but the tap fails. Since the content-addressed v3 library, L1 shrinks only through explicit deletion; uploading a fourth book no longer evicts an older one.
- **I3 — L2 is the source of truth for position**: L3 only stores *which* book; *where* in the book comes from L2.

**Drift scenarios and fallbacks:**

| Scenario                                    | Cause                                                                 | Fallback behavior                                                                                 |
|---------------------------------------------|-----------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| L3 has bookId, L1 doesn't                   | User deleted the book from the web library after reading it          | `Continue reading` label flips to `"(No recent book)"`. Tap is a no-op with status warning.       |
| L3 has title only (legacy v1.3.1 blob)      | User upgraded without opening any book yet                           | Per Q6 → B: **no title-only fallback.** Treat as unresolvable; slot 0 shows `"(No recent book)"` until the user opens a book under v1.4.0, which writes the new keys. CHANGELOG must call this out. |
| L3 has `(title, filename)`, L1 has two books with same title | Duplicate title upload                                              | Use filename as tiebreaker. If `(title, filename)` is still ambiguous, treat as unresolvable and surface `"(No recent book)"` rather than guessing. |
| L3 is empty (first-ever launch)             | Cold install, no book ever opened                                     | `Continue reading` shown as disabled label. Slot is visible but non-functional.                   |
| L2 has no position for the L3 bookId        | Bridge storage write failed mid-save last session                    | `loadBook(resume=true)` handles this today — position defaults to `(0, 0)`.                      |
| L1 empty but L3 present                     | Bridge cleared; WebView localStorage survived                         | Pathological — treat as "disabled Continue" since we can't hydrate a book from L3 alone (no buffer). |

**Testing invariants**: a new test file `tests/continue-reading.test.ts` should cover the drift table above with a mock bridge and fixture `cachedBookList` entries. Each row becomes one test case. This is pure-function-testable once `resolveLastBook(cachedBookList, l3)` is extracted as a helper in `even-client.ts` (or better, into `book-id.ts`).

## 12. Risks & Open Questions for Review

### 12.1 Risks

1. **Discoverability of tap-in-paged-to-flow (§6.1).** If users never find the gesture, the "quick switch" claim is hollow. Mitigation: hint-on-first-use (§6.4.2). **Reviewer: is this acceptable, or should we adopt Option C (overlay) instead?**
2. **State machine edge case: `applySettings` during `settingEditor`.** If the reviewer disagrees with the "early return, don't auto-switch view" approach, alternative is to defer the view switch until `mainMenu`-bound transition. **Reviewer preference?**
3. **Flow position when switching paged→flow mid-reading.** Today, switching mode via Settings re-enters at `chapterIndex/pageIndex/flowWordIndex=0`. With tap-to-switch (Option A), we want "continue where I was in paged" — that means entering flow at `(chapterIndex, pageIndex, flowWordIndex=0)` (page start). **Good enough, or should we track sub-page paged reading offset?** Proposal: page start is good enough; users don't track word-precise paged position anyway.
4. **Clock ticker leaks.** If `stopClockTicker` is not called in every exit path (including uncaught errors), we leak a `setInterval`. Mitigation: also stop on `FOREGROUND_EXIT_EVENT` and `SYSTEM_EXIT_EVENT`. Plus a belt-and-suspenders check in `startClockTicker` that clears an existing id before setting a new one.
5. **Bridge-storage writes during editor commit.** The commit path calls `saveSettingsToBridge` which can take non-trivial time (especially on device with the Flutter-handler flakiness documented in v1.3.1's release notes). Mitigation: fire-and-forget the bridge write, let `applySettings` run synchronously. Loss of the bridge write just means the next app restart doesn't remember the change — acceptable degraded state.
6. **`statusBarPosition='right'` removal is a data migration.** Users with custom saves get silently bumped to `'bottom'`. If any user relied on the vertical bar (none known), they'll notice. Mitigation: CHANGELOG note and the migration code path (not a silent drop).

## 15. Codex Review Recommendations

These are implementation recommendations to fold into the design before Claude starts the code change.

1. **Treat startup ownership as a real implementation change.** The current app registers `onLaunchSource('glassesMenu')` in `main.ts` only after `client.init()` completes, while `EvenEpubClient.init()` already runs splash → initial home rendering. If v1.4.0 wants `glassesMenu` launches to bypass `mainMenu`, the startup flow has to be restructured explicitly rather than described as "unchanged". Recommended shape: decide launch intent before `runStartup()` chooses its first view, or pass a startup mode into `EvenEpubClient`.
2. **Do not implement `Continue reading` as title-only lookup.** Reuse the current `bookId`-aware matching path from `main.ts` / `EvenEpubClient` so duplicate titles do not resume the wrong book. The design should say: resolve from cached metadata by `bookId` first, then fall back to `filename`, then `title`.
3. **Keep bridge settings writes off the critical repaint path.** The draft's `commitEditor()` awaits `saveSettingsToBridge()` before repaint, but current `v1.3.1` intentionally runs bridge writes in parallel with `applySettings()` to avoid sluggish device UI. Recommended behavior: update `config`, call `saveSettings()`, start `saveSettingsToBridge()` without awaiting it, repaint immediately, and surface failure only as a warning/status note.
4. **Split the gesture change from the IA/settings change unless it is proven on device.** Main menu, on-device settings, clock, and right-bar removal are architecturally coherent. The asymmetric tap/double-tap mode switch is the only part that changes the core gesture contract and increases exit distance from flow reading. Recommendation: keep the proposed Phase 1 / Phase 2 split unless device testing shows the gesture is clearly discoverable and not frustrating.
5. **Document the persistence invariants that the new menu depends on.** `mainMenu` is only reliable if three stores stay consistent: cached metadata list (`epub-book-list`), saved positions (bookId/title lanes), and `STORAGE_KEY_BOOK_TITLE`. The implementation should update the design to call out those invariants and define fallback behavior when one lane is stale, especially "last title exists but cached meta is missing".
6. **Keep `ARCHITECTURE.md`, `CHANGELOG.md`, and tests in lockstep with the implementation.** The architecture doc was already behind `v1.3.1`; v1.4.0 should not land without updating the state machine, startup flow, settings persistence narrative, and the exact test-count/test-scope notes after code is finalized.
