# v1.4.3 Design — Menu Selection Box Layout

**Status:** Proposal — not yet implemented. Open decisions enumerated in §10. Review fixes appended 2026-05-15.
**Author:** Andriy (with Claude architect-mode collaboration)
**Target version:** 1.4.3
**Current version:** 1.4.2
**Touches:** `src/even-client.ts` (`rebuildSlots` plus stale main-menu comments), new `src/layout.ts`, new `tests/layout.test.ts`, `package.json`, `app.json`, `index.html`, `CHANGELOG.md`
**Estimated complexity:** Low–medium. Single-touchpoint refactor of `rebuildSlots`; pure-function helpers; small device-spike risk on container z-ordering.

---

## 1. Trigger

Even Hub marketplace tester comment:

> "The selection box UI does not properly adapt to the size of the available options. It is recommended to optimize the layout for a more coordinated display effect."

The complaint is about the highlighted row in the on-glasses list views (`mainMenu`, `settings`, `settingEditor`, `bookPicker`, `chapterList`). It is not about any web-UI element.

---

## 2. Current Behavior

All five glasses list views render through one helper:

```ts
// src/even-client.ts (around lines 892–913)
private async rebuildSlots(labels: string[], selectedSlot: number): Promise<void> {
  for (let i = 0; i < ITEMS_PER_PAGE; i++) {           // ITEMS_PER_PAGE = 4
    const isSelected = i === selectedSlot;
    textContainers.push(new TextContainerProperty({
      xPosition: 0,
      yPosition: i * ROW_HEIGHT,                       // ROW_HEIGHT = 72
      width: DISPLAY_WIDTH,                            // 576
      height: ROW_HEIGHT,                              // 72
      borderWidth: isSelected ? 1 : 0,
      borderColor: 5,
      borderRadius: 8,
      paddingLength: 2,
      containerID: i + 1,
      containerName: `slot-${i}`,
      content: labels[i] ?? '',
      isEventCapture: isSelected ? 1 : (selectedSlot < 0 && i === 0 ? 1 : 0),
    }));
  }
  await this.bridge.rebuildPageContainer(...);
  notifyTextUpdate();
  resetGestureState();
}
```

Two consequences:

1. **The highlight is full display width** (`576 px`) regardless of label length. `"ON"`, `"Settings"`, `"60%"` and `"Continue reading"` all sit inside the same 576-px outline. With most labels under 12 characters (~120 px of rendered glyph), the border feels like a banner stretched across a mostly-empty row.
2. **Four slots are always rendered, even when the menu has fewer items.** Empty slots have no border and no content, but they occupy 72 px each of vertical real estate, leaving visible gaps:
   - `mainMenu` has 3 items → 1 blank slot at bottom.
   - Binary settings editors (`hyphenation`, `statusBarPosition`, `readingMode`) have 2 items → 2 blank slots at bottom.

The combination produces what the tester called "uncoordinated."

## 3. SDK Constraints That Bound the Design

Verified against the installed `node_modules/@evenrealities/even_hub_sdk/dist/index.d.ts` (package v0.0.10).

- **`TextContainerProperty` fields:** `xPosition, yPosition, width, height, borderWidth, borderColor, borderRadius, paddingLength, containerID, containerName, isEventCapture, content`. **No** `textColor`, no `textAlign`, no font / size / weight, no opacity.
- **Max 12 total containers per page; max 8 `textObject` entries; exactly one `isEventCapture=1` per page.** This design uses at most 5 text containers, so it stays under both caps. The capturing container's visual rect must cover the full swipe area or first swipes are dropped on hardware — empirically verified during the v1.2.0 Text-height work (`docs` lineage / memory note `project_g2_display_quirks.md`).
- **No SDK API for "intensity," "brightness," or any z-index hint.** Container layering behavior with overlapping rects is **undocumented**. The installed `even-toolkit` uses overlay-first pages (`node_modules/even-toolkit/glasses/bridge.ts`), which is a useful precedent but not a substitute for device verification. **This is the load-bearing unknown for the design below** and is the focus of the §8 device spike.
- **Monospace glyph pitch ≈ 9.76 px** for narrow glyphs, ≈ 12 px for wide / CJK glyphs. Derived from `src/paginator.ts:24` (`maxChars = wideGlyphs ? 48 : 59` against `DISPLAY_WIDTH = 576`).
- **Centering text inside a container** must be done by left-padding the `content` string with spaces — the SDK does not offer alignment. Precedent: `getWelcomeContainers` at `src/even-client.ts:280`.

## 4. Proposed Layout

Each list-view page becomes:

```
                     ┌──────────────────────────┐
                     │     Continue reading     │   ← centered horizontally,
                     └──────────────────────────┘     width = page-max label
                     ┌──────────────────────────┐
                     │       Library (3)        │
                     └──────────────────────────┘
                     ┌──────────────────────────┐
                     │        Settings          │   ← only the selected row
                     └──────────────────────────┘     has borderWidth: 1

   ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░    ← invisible full-screen
   ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░      event-capture overlay
```

### 4.1 Containers per page

| # | Role | Geometry | `isEventCapture` | Border | Content |
|---|------|----------|------------------|--------|---------|
| 1 | **Swipe catcher** | `x=0 y=0 576×288` | **1** | 0 | `""` (empty) |
| 2..N+1 | **Option rows** | centered x, `width = pageMaxLabelWidth`, `height = ROW_HEIGHT`, `y` from `computeRowOffsets()` | 0 | `borderWidth: 1` only on the selected row | space-centered label |

`N` is the number of *actual* options on the current page (1..4). Total containers per page: `1 + N` ≤ 5, well under the SDK's 12 total-container cap and 8-text-container cap.

### 4.2 Sizing

```ts
// Pseudocode for the new helpers (in src/layout.ts)

const CHAR_PITCH_PX = 9.76;     // 576 / 59
const MIN_BOX_PX    = 160;      // ~16 cells — keeps "ON" from looking tiny
const EDGE_MARGIN   = 16;       // breathing room at left/right
const BORDER_INSET  = 4;        // visual border + inner padding allowance

function computeBoxWidthPx(labels: string[]): number {
  const longest = Math.max(0, ...labels.filter(s => s).map(s => s.length));
  const raw     = Math.ceil(longest * CHAR_PITCH_PX) + 2 * BORDER_INSET;
  return clamp(raw, MIN_BOX_PX, DISPLAY_WIDTH - 2 * EDGE_MARGIN);
}

function trimTrailingEmptySlots(labels: string[]): string[] {
  const visible = labels.slice(0, ITEMS_PER_PAGE).map(l => l ?? '');
  while (visible.length > 0 && visible[visible.length - 1].length === 0) {
    visible.pop();
  }
  return visible;
}

function computeRowOffsets(n: number): number[] {
  const used   = n * ROW_HEIGHT;
  const top    = Math.max(0, Math.floor((DISPLAY_HEIGHT - used) / 2));
  return Array.from({ length: n }, (_, i) => top + i * ROW_HEIGHT);
}

function centerLabel(label: string, boxChars: number): string {
  const pad = Math.max(0, Math.floor((boxChars - label.length) / 2));
  return ' '.repeat(pad) + label;
}
```

- **All option rows on a page share `pageMaxLabelWidth`** (preferred — stable left edge as the highlight moves) rather than each row shrinking to its own label width. See §10 Q1 for the alternative.
- `boxChars = Math.floor(pageMaxLabelWidth / CHAR_PITCH_PX)`.
- For `N = ITEMS_PER_PAGE`, `top = 0`, so the layout collapses to the current grid.
- The implementation should trim only **trailing** empty slots, not filter all empty labels, so future callers cannot accidentally shift `selectedSlot` by inserting an internal blank/separator row.

### 4.3 Tap & swipe routing

The swipe-catcher container (container 1) is `isEventCapture = 1` and covers the full display, so:

- Every swipe lands inside the capturing rect → no swipe is dropped, regardless of where on the temple the user gestures. This is consistent with the v1.2.0 finding that the event-capture container must cover the swipe area.
- Tap (`CLICK_EVENT`) is routed to the same container. We continue to use our own `mainMenuSelectedIndex` / `settingsListSelectedIndex` / `editorSelectedIndex` for "what's highlighted" — the device's `currentSelectItemIndex` is already ignored. No change to `onMainMenuSelect()` etc.

## 5. Wiring

Single touchpoint: `rebuildSlots(labels, selectedSlot)` in `src/even-client.ts`. Every list view already routes through it — `showMainMenu`, `showSettingsMenu`, `showSettingEditor`, `rerenderEditor`, `showBookPicker`, `showChapterList`. No caller changes needed; no `ViewState` changes.

`rebuildSlots` becomes:

```ts
private async rebuildSlots(labels: string[], selectedSlot: number): Promise<void> {
  const visibleLabels = trimTrailingEmptySlots(labels);
  const n              = visibleLabels.length;
  const boxWidthPx     = computeBoxWidthPx(visibleLabels);
  const boxChars       = Math.floor(boxWidthPx / CHAR_PITCH_PX);
  const xPosition      = Math.floor((DISPLAY_WIDTH - boxWidthPx) / 2);
  const yPositions     = computeRowOffsets(n);

  const containers: TextContainerProperty[] = [];

  // Container 1: invisible full-screen event-capture overlay.
  containers.push(new TextContainerProperty({
    xPosition: 0, yPosition: 0,
    width: DISPLAY_WIDTH, height: DISPLAY_HEIGHT,
    borderWidth: 0, borderColor: 0,
    paddingLength: 0,
    containerID: 1, containerName: 'swipe',
    content: '',
    isEventCapture: 1,
  }));

  // Containers 2..N+1: visible option rows.
  for (let i = 0; i < n; i++) {
    const isSelected = i === clamp(selectedSlot, 0, n - 1);
    containers.push(new TextContainerProperty({
      xPosition,
      yPosition: yPositions[i],
      width: boxWidthPx, height: ROW_HEIGHT,
      borderWidth: isSelected ? 1 : 0,
      borderColor: 5, borderRadius: 8,
      paddingLength: 2,
      containerID: i + 2, containerName: `slot-${i}`,
      content: centerLabel(visibleLabels[i], boxChars),
      isEventCapture: 0,
    }));
  }

  await this.bridge.rebuildPageContainer(new RebuildPageContainer({
    containerTotalNum: containers.length,
    textObject: containers,
  }));
  notifyTextUpdate();    // arm the 40 ms phantom-suppression window
  resetGestureState();   // clear stale cross-view tap/scroll history
}
```

The `notifyTextUpdate()` + `resetGestureState()` call order remains exactly as in v1.4.2 — the phantom-SCROLL fix is unchanged. Note that current `src/even-client.ts` comments still say "80 ms" in a few places; the installed `even-toolkit/glasses/gestures.ts` constant is `SCROLL_SUPPRESS_AFTER_TEXT_MS = 40`, so update those comments during the implementation pass.

## 7. Tests

### 7.1 New — `tests/layout.test.ts`

Pure-function tests against `src/layout.ts`:

- `computeBoxWidthPx`:
  - Single short label clamps to `MIN_BOX_PX`.
  - Longest label drives width; other labels do not.
  - Very long label clamps to `DISPLAY_WIDTH - 2*EDGE_MARGIN`.
  - Empty string in the label array is ignored.
  - All-empty input returns `MIN_BOX_PX` instead of producing `-Infinity`/`NaN`.
- `trimTrailingEmptySlots`:
  - Removes trailing empty rows from fixed 4-slot caller arrays.
  - Preserves internal empty strings so `selectedSlot` indexes are not shifted.
- `computeRowOffsets`:
  - `n=4` returns `[0, 72, 144, 216]` (regression-equivalent of today's grid).
  - `n=3` returns rows symmetric around `DISPLAY_HEIGHT/2`.
  - `n=2` returns rows symmetric around `DISPLAY_HEIGHT/2`.
  - `n=1` returns `[(DISPLAY_HEIGHT - ROW_HEIGHT) / 2]`.
- `centerLabel`:
  - Even and odd `box - label` deltas.
  - Label longer than the box → returned unchanged (no negative padding, no truncation).

### 7.2 Existing tests must continue passing

`npm run test` baseline: 93 tests at v1.4.2. Layout changes do not touch state, persistence, or gesture-pipeline code, so the existing suites should remain green without modification.

## 8. Device Spike (Recommended Before Full Implementation)

Two SDK behaviors are not documented and must be verified on real G2 hardware before this design is committed to.

### 8.1 Z-ordering / occlusion of overlapping containers

**Hypothesis:** A `TextContainerProperty` with `borderWidth: 0`, `borderColor: 0`, `content: ''`, and `paddingLength: 0` paints **nothing** to the display surface, so visible option containers render normally when the empty full-screen event-capture container is declared **before** them in `textObject[]` (matching the installed `even-toolkit` overlay pattern).

**Risk:** If the device clears the rect for the full-screen empty container or if event routing depends on the topmost visual container rather than the sole `isEventCapture=1` container, option text could be hidden or gestures could be lost.

**Spike steps:**
1. Build a one-off page with two containers:
   - Container A first: `x=0 y=0 w=576 h=288 border=0 content="" isEventCapture=1` → full-screen overlay.
   - Container B second: `x=100 y=100 w=200 h=72 border=1 content="HELLO" isEventCapture=0` → visible boxed text.
2. Push the page to a real G2 via `npm run dev` + scan QR. Verify "HELLO" is still visible.
3. Tap and swipe anywhere on the temple. Verify the swipe-catcher receives both event types.
4. Optional diagnostic if step 2 or 3 fails: reverse the declaration order to learn whether paint order or event routing is the failing constraint.

**Decision gate:** If "HELLO" is visible and full-screen taps/swipes route through the overlay-first page → primary design (§4–5) is viable. If text is hidden or gestures are lost → fall back to §9.

### 8.2 Tap dispatch with a single non-row event-capture container

**Hypothesis:** With one `isEventCapture: 1` container that *isn't* the visually-selected row, `CLICK_EVENT` still fires with our intended semantics, and we continue to drive selection from our own `mainMenuSelectedIndex` etc.

**Risk:** If the device interprets the event-capture container's `currentSelectItemIndex` specially (e.g. emits a list-event with a stale index that our action-map mis-handles), taps could be lost or mis-routed.

**Spike steps:** Reuse the §8.1 page; tap the temple; log every event arriving in `onEvenHubEvent`. Confirm a single `CLICK_EVENT` per tap, no extra list-events, and that `mapGlassEvent` returns `SELECT_HIGHLIGHTED`.

**Decision gate:** If taps route cleanly → primary design viable. If extra events appear → fall back to §9, where the event-capture target is limited to the selected row's full-width y-band.

## 9. Fallback Design (If the Spike in §8 Fails)

If the invisible overlay either occludes the option rows or breaks tap routing, fall back to the **selected-row-strip-capture** model:

- N visible option rows, each centered with `width = pageMaxLabelWidth` as in §4.
- Add **one extra invisible capture strip behind the selected row only**, sized to a full-display-width strip at the same y-position (`x=0 y=row_y w=576 h=ROW_HEIGHT`), `isEventCapture: 1`, no border. This widens the swipe-capture area for the selected row to the whole display width on that row.
- The visible selected row keeps `borderWidth: 1` but **must remain `isEventCapture: 0`**. Do not mark both the strip and the visible row as capture targets; the SDK requires exactly one `isEventCapture=1` container per page.
- Unselected rows are decorative (`isEventCapture: 0`, no border).

Limitation: swipes on rows other than the selected row's y-band would still be lost (the v1.2.0 finding). The user must swipe **on the selected row's band**, matching today's selected-row capture behavior, while the visible border can still shrink to the label-width box. This improves visual coordination but does not provide the full-screen swipe target of the primary overlay design.

Container budget: `N + 1` total (4 option rows + 1 invisible widener = 5).

## 10. Open Decisions

To resolve before implementation:

1. **Width selection policy.** Should `boxWidthPx` be derived from the **page-max** label (proposed; stable left edge) or **per-row** (each row independently sized; tightest fit but the left edge jitters as the highlight moves)?
2. **Content alignment inside the box.** Center the label (proposed, mirrors `getWelcomeContainers`) or left-align with `paddingLength: 2` of leading space?
3. **Minimum box width.** Is 160 px (≈16 cells) the right floor, or should the minimum be smaller (e.g. 100 px) for editors where every label is 4–6 chars?
4. **`borderColor: 5` retention.** Keep the current border color, or switch to `borderColor: 0` (default) and see if it renders more cleanly? The toolkit defaults to `0` throughout (`node_modules/even-toolkit/glasses/bridge.ts` shows `borderColor: 0` in every helper). The app's current `5` may have been a copy-paste from an older example.
5. **Selection-box height.** Keep `ROW_HEIGHT = 72`, or tighten to `~48` for binary editors where the box height is what makes them look "banner-ish"? The current 72 px is set by `DISPLAY_HEIGHT / ITEMS_PER_PAGE` — decoupling it would let editors with few items use a tighter row.
6. **`v1.4.0-on-device-settings-and-menu.md` decision Q3 ("stable 3-slot layout").** Q3 protects the three semantic main-menu choices and the disabled `"(No recent book)"` slot behavior; this proposal keeps those. What changes is the implementation detail that `showMainMenu` currently pads a fourth blank render slot. Update the stale `src/even-client.ts` comments ("Slot 3 is blank", "3 fixed slots") so they describe three semantic options plus dynamic render-row centering, not a permanent four-row grid.

## 12. Out of Scope

- **Brightness / text intensity.** Investigated 2026-05-04 and parked as not feasible — the SDK exposes no `textColor` field. See `project_sdk_capability_surface.md` memory note. Do not bundle.
- **Font size / weight changes.** Same SDK constraint.
- **Animated highlight transitions.** SDK has no animation primitive; container changes require either `rebuildPageContainer` (flicker) or `textContainerUpgrade` (text-only). Neither supports a moving border.
- **Per-item icons (e.g. a check-mark next to the current setting value).** Possible via `paginator`-style ASCII characters but out of scope here; could be a follow-up v1.4.4.
- **Web UI layout.** Tester comment is about the on-glasses display; the web reader is unaffected.
