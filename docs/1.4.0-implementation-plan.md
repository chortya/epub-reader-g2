## 1. What this document is

The design doc (`1.4.0-on-device-settings-and-menu.md`) answers *what we're building and why*. This document answers *how we're going to build it without breaking the app mid-stage*. It is a commit-by-commit execution plan, with every stage scoped small enough that:

- Tests stay green at every stage boundary.
- `npm run build` is clean at every stage boundary.
- The app still runs in both the simulator and on device (when testable) after every commit.
- Rollback of any single stage reverts one commit — no cross-stage entanglement.

Codex is asked to critique:

1. **Staging** — does the 10-stage split make sense, or should stages merge / split?
2. **Dependencies** — is the DAG correct, or do I have a missing edge that would cause a stage-N commit to leave the app broken?
3. **TDD coverage** — do the listed tests actually exercise the behavior Codex #2, #3, #5 asked for, or are they surface-level?
4. **Risk mitigation** — is the per-stage risk list complete, or am I under-selling any?
5. **Rollback** — does every stage have an obvious rollback, or are some one-way doors?

This document does **not** re-justify the design choices — those are frozen in §16 of the design doc. If a design decision looks wrong during implementation, **stop and amend the design doc first**, do not improvise.

## 2. Staging principles

### 2.1 Commit-boundary invariants (non-negotiable)

At every stage boundary, on the main branch:

- `npm run test` is green.
- `npm run build` is clean, no new warnings.
- `npm run pack` would succeed (not required to run every time, but the app is in a packable state).
- The app boots end-to-end in the simulator (`npm run dev:sim`) with no thrown errors in the console.
- No commented-out production code. No `// TODO: fix later` placeholders that block obvious follow-up.
- If the stage involves removing code, the removed code is **deleted**, not commented — per the repo's code-style rule in CLAUDE.md.

### 2.2 Ordering rules

- **Smallest blast radius first.** Pure cleanups (Stage 1) and pure helpers (Stage 2) land before any code that integrates them.
- **TDD for every pure helper.** Test file written first, assertions failing, then minimum code to pass. Stage 2 is entirely TDD; stages 3–7 mix TDD (for any new helper extracted along the way) with integration-level manual verification.
- **No forward-references.** A stage never writes code that depends on a later stage's work. If the forward dependency is unavoidable, re-order.
- **Every stage has a one-line commit message** in imperative mood, matching the repo's convention. Listed per-stage below.

### 2.3 What "done" means for a stage

A stage is done when:
- Its listed files are modified exactly as described.
- Its listed tests are added (RED-first for new helpers) and passing.
- Its commit is written with the prescribed message.
- Any manual verification step (simulator smoke-test, device test) has passed.

### 3.1 Edges — rationale

| Edge | Why it exists |
|---|---|
| 0 → 1 | Stage 1 changes `tests/settings-persistence.test.ts`; Stage 0 ensures `app.json.version === package.json.version === 1.4.0` so that test stays green. |
| 0 → 2 | Same — any test file changes must happen on top of a valid version state. |
| 1 → 3 | Stage 3 writes new keys in `savePagedPosition`/`saveFlowPosition`; those functions live in `even-client.ts` which Stage 1 rewrites (right-bar branches). Serializing avoids merge conflicts. |
| 1 → 4 | Stage 4 rewrites the footer rendering in `showPage`/`showFlowFrame`; Stage 1 removes the right-bar branches from the same functions. Serialize to avoid diff conflicts. |
| 2 → 4 | Stage 4 consumes `formatStatusLine` introduced in Stage 2. |
| 2 → 5 | Stage 5 consumes `pickInitialView` introduced in Stage 2. |
| 5 → 6 | Stage 6's settings menu is reached by tapping slot 2 on `mainMenu` (introduced in Stage 5). |
| 3 → 5 | Stage 5's launch-intent-aware startup needs the same L3 data Stage 7 later uses for slot-0 Continue Reading. Without Stage 3, `glassesMenu` direct-resume would be forced to fall through to `mainMenu` in all cases. |
| 3 → 7 | Stage 7's `resolveLastBook` reads the L3 keys that Stage 3's writers populate. If Stage 7 runs before Stage 3, Continue Reading would always fall through to "(No recent book)". |
| 5 → 7 | Stage 7 renders into `mainMenu`'s slot 0, introduced in Stage 5. |
| 4, 6, 7 → 8 | Docs must reflect the final code shape; run docs last to avoid rewriting. |
| 8 → 9 | Verification is last. |

### 3.2 Edges that **don't** exist — and why

- **Stage 4 and Stage 5 are independent.** Clock ticker doesn't touch view-state-machine code; mainMenu doesn't touch reading-view rendering. They can run in either order or in parallel.
- **Stage 3 and Stage 2 are independent.** Stage 3 adds bridge-key writers in `even-client.ts`; Stage 2 adds pure helpers in `constants.ts`, `book-id.ts`, `src/launch.ts`. No file overlap.
- **Stage 6 does not depend on Stage 4.** Settings editing is independent of clock rendering. If Stage 4 is deferred for any reason (e.g. simulator flicker investigation), Stage 6 can still ship.

### Stage 5 — MainMenu view + startup restructuring

**Goal:** Splash → mainMenu (3 slots: Continue / Library / Settings). Restructure `main.ts` to register `onLaunchSource` before `client.init()`; use `pickInitialView` to decide the post-splash view.

**Depends on:** Stage 2 (`pickInitialView`, `LaunchIntent`), Stage 3 (L3 keys available for resolvable `glassesMenu` startup).

**Files**

- `src/even-client.ts`:

    - `GO_BACK` → `bridge.shutDownPageContainer(1)` (exit app).
  - `onEvenHubEvent` amendments to existing views:
    - `bookPicker` `GO_BACK` now routes to `showMainMenu()` (was: exit-app).
    - `library` `GO_BACK` now routes to `showMainMenu()` (was: `bookPicker` or `welcome`).
- `src/main.ts`:
  - Move `bridge.onLaunchSource(...)` registration to **before** `client.init()`. The callback calls `client.setLaunchIntent(source)`.
  - `client.init()` now reads `this.launchIntent` inside `runStartup`. If still `null` at that point, treat as `'appMenu'` → `mainMenu` (design §3.1a decision Q7 → A).

**Approach**
1. Extend `ViewState` and `setLaunchIntent`.
2. Wire `main.ts` registration-order change.
3. Implement startup-time `lastBook` resolution using the Stage 3 keys plus `resolveLastBook(...)`. This is for post-splash routing only; slot-0 UI wiring remains Stage 7.
4. Implement `showMainMenu` with 3 static labels (slot 0 reads `"Continue reading"` placeholder; slot 1 reads `Library (${N})`; slot 2 reads `"Settings"`).
5. Extend `onEvenHubEvent` for `mainMenu`. Slot-2 tap is a log-only no-op until Stage 6.
6. Repoint `bookPicker`/`library` dbl-tap to `mainMenu`.
7. Exercise `tests/launch-intent.test.ts` (written in Stage 2) — it should have been failing until now against the integration; now it passes end-to-end.

**Tests added:** 0 new (Stage 2 pre-wrote `tests/launch-intent.test.ts`).

**Commit:** `feat: main menu with launch-intent-aware startup`

**Rollback:** single-commit revert restores the v1.3.1 bookPicker-first flow. No persistence shape change here.

**Risks** (highest of any stage)
- **MockBridge `onLaunchSource` timing.** Today the mock fires the callback with `setTimeout(cb, 50)`. After re-registration-order change, `client.init()` will race with that 50 ms. Within `init`, splash runs for `minTimeMs: 2000` (from `showSplashThenHome`), so `pickInitialView` is called ~2 s after mount — the mock callback will always have fired by then. **Verified safe for simulator.** On device, the real SDK timing is unknown; `pickInitialView` falls back to `mainMenu` if still `null`, so the worst case is the user sees mainMenu instead of direct-resume — acceptable.
- **Exit-app UX regression.** dbl-tap from `bookPicker` used to exit; now it goes to `mainMenu`. Some users may habitually dbl-tap to exit and end up stuck in the mainMenu → one extra dbl-tap to exit. Mitigated by CHANGELOG callout.
- **Chapter-list → mainMenu**: user orientation changes. Not a correctness issue but a UX one; documented in design §3.1 as acceptable.

    await showSettingsMenu();

7. Replace Stage 5 slot-2 stub.
8. Manual simulator: change every setting; verify commit writes to both LS and bridge; verify cancel restores; verify readingMode change repaginates but does not jump to reading (per guard).

**Tests added:** 0 new (Stage 2 pre-wrote `applyEditorValue` and `formatSettingsRow` tests). Optional: a test for the `applySettings` guard — but that's integration-level and requires a mock client. Skip for Phase 1; rely on simulator.

## 6. Risk register (aggregate)

Cross-stage risks in decreasing likelihood:

1. **Stage 5 `onLaunchSource` timing on device.** Mitigated by mainMenu fallback; worst case is the user sees mainMenu briefly instead of direct-resume. **Watch during device pass.**
2. **Stage 4 `textContainerUpgrade` invariant in paged path.** New pattern. **Watch for flicker on simulator; confirm on device.**
3. **Stage 3 write amplification × flaky bridge.** 3 writes per save instead of 1. No known problem, but write-failure blast radius grows. **Watch for L3 incomplete-state in Stage 7 Continue Reading drift.**
4. **Stage 6 `applySettings` guard.** If the guard is wrong, changing `readingMode` in settings could jump the user into reading mid-edit, losing the "return to settings list" flow. **Simulator test every setting.**
5. **Upgrade migration (Stages 1 + 3 combined).** Users on v1.3.1 with `'right'` saved and no opened book get both the `'right' → 'bottom'` migration *and* the empty-L3 "(No recent book)" path on first v1.4.0 boot. Both are called out in CHANGELOG; no data loss.
6. **Stage 0/8 manifest drift.** If any file is forgotten in the version bump, `app-json.test.ts` catches `package.json ≠ app.json`, but `index.html` / `CLAUDE.md` / `ARCHITECTURE.md` could ship stale strings. **Grep-check before Stage 9 pack.**

## 7. Execution modes

Three ways to run this plan:

### 7.1 Solo, commit-by-commit

Fastest when one person owns the whole change. Each stage takes 20–90 minutes based on §4's size estimates. Total wall-clock: ~6–10 hours including simulator passes.

### 7.2 Claude orchestrator + general-purpose agent per stage

Spawn one `general-purpose` agent per stage. Each agent gets:
- This plan (`docs/1.4.0-implementation-plan.md`).
- The design doc.
- The stage's exact file-touch list and commit message.
- Instruction to stop at commit-boundary invariants.

The orchestrator reviews each commit before unblocking the next stage's agent. Slightly higher total wall-clock but lower-risk per commit; good for when the user wants to review diffs rather than drive.

### 7.3 Hybrid

User drives stages 0, 1, 5 (UX-critical) personally; hand off Stages 2, 3, 4, 6, 7, 8 to agents. Stage 9 verification is user-only.

**Recommended:** 7.2 for Stages 0–4 (pure / low-risk), 7.3 for Stages 5–9.
